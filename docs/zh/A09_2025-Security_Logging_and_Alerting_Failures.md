# A09:2025 安全日志与告警失效 ![icon](../assets/TOP_10_Icons_Final_Security_Logging_and_Monitoring_Failures.png){: style="height:80px;width:80px" align="right"}


## 背景

安全日志与告警失效（Security Logging & Alerting Failures）继续保持在第9位。该类别名称略有调整，以强调告警功能在促使对 relevant 日志事件采取行动方面的重要性。该类别在数据中始终被低估，并且第三次由社区调查参与者投票进入榜单。该类别极难测试，在CVE/CVSS数据中代表性很低（仅723个CVE）；但它对可见性、事件告警和取证可能非常有影响力。该类别包括 *日志文件输出编码处理不当（CWE-117）、将敏感数据插入日志文件（CWE-532）以及日志记录不足（CWE-778）* 等问题。

## 描述

如果没有日志记录和监控，攻击和入侵就无法被检测到；如果没有告警，在安全事件期间就很难快速有效地响应。当日志记录、持续监控、检测和告警不足，无法启动主动响应时，就会出现以下情况：


* 可审计事件（如登录、登录失败和高价值交易）未被记录或记录不一致（例如，只记录成功的登录，而不记录失败的尝试）。
* 警告和错误没有生成、生成不足或生成不清晰的日志消息。
* 日志的完整性未得到适当保护，容易被篡改。
* 应用程序和API的日志未被监控以发现可疑活动。
* 日志仅存储在本地，未进行适当备份。
* 未建立或有效的适当告警阈值和响应升级流程。告警未在合理的时间内被接收或审查。
* 渗透测试和动态应用程序安全测试（DAST）工具（如Burp或ZAP）的扫描不会触发告警。
* 应用程序无法实时或近实时地检测、升级或告警主动攻击。
* 您容易受到敏感信息泄露的威胁，因为日志和告警事件对用户或攻击者可见（参见 [A01:2025-失效的访问控制](A01_2025-Broken_Access_Control.md)），或者因为记录了不应记录的敏感信息（如PII或PHI）。
* 如果日志数据未正确编码，您容易受到对日志或监控系统的注入或攻击。
* 应用程序缺失或错误处理了错误和其他异常情况，导致系统不知道发生了错误，因此无法记录存在问题。
* 缺少或过时地发布告警的充分"用例"，无法识别特殊情况。
* 过多的误报告警使得无法区分重要告警和不重要告警，导致它们被识别得太晚或根本未被识别（SOC团队的物理过载）。
* 检测到的告警无法被正确处理，因为该用例的剧本不完整、过时或缺失。


## 预防措施

开发人员应根据应用程序的风险实施以下部分或全部控制措施：


* 确保所有登录、访问控制和服务器端输入验证失败都可以被记录，并包含足够的用户上下文以识别可疑或恶意账户，且保留足够长的时间以允许延迟的取证分析。
* 确保应用程序中包含安全控制的每个部分都被记录，无论其成功或失败。
* 确保日志以日志管理解决方案可以轻松消费的格式生成。
* 确保日志数据被正确编码，以防止对日志或监控系统的注入或攻击。
* 确保所有交易都有带有完整性控制的审计跟踪，以防止篡改或删除，例如仅追加的数据库表或类似机制。
* 确保所有抛出错误的交易都被回滚并重新开始。始终安全地失败（fail closed）。
* 如果您的应用程序或其用户行为可疑，请发出告警。为此主题为您的开发人员创建指导，以便他们可以针对此进行编码，或购买专门的系统。
* DevSecOps和安全团队应建立有效的监控和告警用例，包括剧本，以便安全运营中心（SOC）团队能够快速检测和响应可疑活动。
* 在您的应用程序中添加"蜜标"（honeytokens）作为攻击者的陷阱，例如放入数据库、数据中，作为真实和/或技术用户身份。由于它们在正常业务中不会被使用，任何访问都会生成可以被告警的日志数据，且几乎没有误报。
* 行为分析和AI支持可以作为可选的附加技术，以支持低误报率的告警。
* 建立或采用事件响应和恢复计划，例如美国国家标准与技术研究院（NIST）800-61r2或更新版本。教您的软件开发人员应用程序攻击和事件的样子，以便他们能够报告它们。

有商业和开源的应用程序保护产品，如OWASP ModSecurity核心规则集，以及开源日志关联软件，如Elasticsearch、Logstash、Kibana（ELK）堆栈，它们具有自定义仪表板和告警功能，可能有助于您解决这些问题。还有商业可观测性工具可以帮助您接近实时地响应或阻止攻击。


## 攻击场景示例

**场景 #1：** 一家儿童健康计划提供商的网站运营商由于缺乏监控和日志记录而无法检测到入侵。一个外部方告知该健康计划提供商，攻击者访问并修改了超过350万名儿童的数千条敏感健康记录。事后审查发现，网站开发人员未解决重大漏洞。由于系统没有日志记录或监控，数据泄露可能自2013年以来一直在进行，持续时间超过七年。

**场景 #2：** 一家大型印度航空公司发生数据泄露，涉及数百万乘客超过十年的个人数据，包括护照和信用卡数据。数据泄露发生在一家第三方云托管提供商处，该提供商在一段时间后通知了航空公司。

**场景 #3：** 一家大型欧洲航空公司遭受了需要向GDPR报告的数据泄露。据报道，该泄露是由支付应用程序安全漏洞被攻击者利用造成的，攻击者窃取了超过40万条客户支付记录。该航空公司因此被隐私监管机构罚款2000万英镑。
