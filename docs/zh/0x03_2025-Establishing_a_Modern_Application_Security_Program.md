# 建立现代应用程序安全计划

OWASP Top Ten 列表是意识提升文档，旨在引起人们对所涵盖主题中最关键风险的关注。它们并非完整的清单，而只是一个起点。在此列表的先前版本中，我们建议启动应用程序安全计划作为避免这些风险及更多风险的最佳方式。在本节中，我们将介绍如何启动和构建现代应用程序安全计划。

如果您已经拥有应用程序安全计划，请考虑使用 [OWASP SAMM（软件保证成熟度模型）](https://owasp.org/www-project-samm/) 或 DSOMM（DevSecOps 成熟度模型）对其进行成熟度评估。这些成熟度模型全面而详尽，可帮助您确定在扩展和成熟化计划方面应重点投入精力的方向。请注意：您无需完成 OWASP SAMM 或 DSOMM 中的所有内容才能做好工作，它们旨在为您提供指导并提供多种选择。它们并非旨在提供无法达到的标准或描述负担不起的计划。它们内容广泛，旨在为您提供许多想法和选择。

如果您是从零开始启动计划，或者发现 OWASP SAMM 或 DSOMM 对您的团队来说"太多了"，请查看以下建议。

### 1. 建立基于风险的投资组合方法：

* 从业务角度识别应用程序组合的保护需求。这在一定程度上应由隐私法和其他与被保护数据资产相关的法规驱动。

* 建立[通用的风险评级模型](https://owasp.org/www-community/OWASP_Risk_Rating_Methodology)，使用一致的可能性和影响因子集合，反映您组织对风险的容忍度。

* 据此衡量并优先处理所有应用程序和 API。将结果添加到您的[配置管理数据库（CMDB）](https://de.wikipedia.org/wiki/Configuration_Management_Database)中。

* 建立保证指南，正确定义所需的覆盖范围和严格程度。

### 2. 以坚实基础赋能：

* 建立一套重点明确的政策和标准，为所有开发团队提供应用程序安全基线。

* 定义一组通用的可重用安全控制措施，以补充这些政策和标准，并提供关于其使用的设计和开发指导。

* 建立应用程序安全培训课程，针对不同开发角色和主题进行必修和定向培训。

### 3. 将安全集成到现有流程中：

* 将安全实施和验证活动定义并集成到现有的开发和运营流程中。

* 活动包括威胁建模、安全设计和设计审查、安全编码和代码审查、渗透测试以及修复。

* 为开发和项目团队提供主题专家和支持服务，以确保成功。

* 审查当前的系统开发生命周期以及所有软件安全活动、工具、政策和流程，然后将其文档化。

* 对于新软件，在系统开发生命周期（SDLC）的每个阶段添加一个或多个安全活动。下面我们将提供许多建议。确保在每个新项目或软件计划上执行这些新活动，这样您就会知道每个新软件都将以您组织可接受的安全态势交付。

* 选择您的活动，以确保最终产品满足您组织可接受的风险水平。

* 对于现有软件（有时称为遗留软件），您需要制定正式的维护计划，请在下面"运营和变更管理"部分中查看如何维护安全应用程序的建议。

### 4. 应用程序安全教育：

* 考虑启动安全冠军计划，或为您的开发人员启动通用安全教育计划（有时称为倡导或安全意识计划），教他们您希望他们了解的所有内容。这将使他们保持最新状态，帮助他们知道如何安全地完成工作，并使您工作场所的安全文化更加积极。这通常还能改善团队之间的信任，使工作关系更加愉快。OWASP 通过 [OWASP 安全冠军指南](https://securitychampions.owasp.org/) 为您提供支持，该指南正在逐步扩展。

* OWASP 教育项目提供培训材料，帮助教育开发人员了解 Web 应用程序安全。如需通过实践学习漏洞知识，请尝试 [OWASP Juice Shop 项目](https://owasp.org/www-project-juice-shop/) 或 [OWASP WebGoat](https://owasp.org/www-project-webgoat/)。要保持最新状态，请参加 [OWASP AppSec 会议](https://owasp.org/events/)、[OWASP 会议培训](https://owasp.org/events/) 或本地 [OWASP 分会](https://owasp.org/chapters/) 会议。

### 5. 提供管理层可见性：

* 用指标进行管理。根据捕获的指标和分析数据推动改进和资金决策。指标包括遵守安全实践和活动的情况、引入的漏洞、缓解的漏洞、应用程序覆盖范围、按类型和实例计数计算的缺陷密度等。

* 分析实施和验证活动的数据，寻找根本原因和漏洞模式，以推动整个企业的战略性和系统性改进。从错误中学习，并提供积极的激励措施以促进改进。

## 建立并使用可重复的安全流程和标准安全控制

### 需求与资源管理阶段：

* 与业务部门收集和协商应用程序的业务需求，包括关于所有数据资产的机密性、真实性、完整性和可用性的保护需求，以及预期的业务逻辑。

* 汇编技术需求，包括功能性和非功能性安全需求。OWASP 建议您使用 [OWASP 应用程序安全验证标准（ASVS）](https://owasp.org/www-project-application-security-verification-standard/) 作为为您的应用程序设定安全需求的指南。

* 规划和协商涵盖设计、构建、测试和运营所有方面的预算，包括安全活动。

* 将安全活动添加到您的项目计划中。

* 在项目启动时以安全代表的身份介绍自己，这样他们就知道该与谁交谈。

### 征求建议书（RFP）与合同签订：

* 与内部或外部开发人员协商需求，包括关于您的安全计划的安全指南和安全需求，例如 SDLC、最佳实践。

* 评估所有技术需求的满足情况，包括规划和设计阶段。

* 协商所有技术需求，包括设计、安全和服务水平协议（SLA）。

* 采用模板和清单，例如 [OWASP 安全软件合同附件](https://owasp.org/www-community/OWASP_Secure_Software_Contract_Annex)。<br>**注意：** *该附件适用于美国合同法，因此在使用样本附件之前请咨询合格的法律意见。*

### 规划与设计阶段：

* 与开发人员和内部利益相关者（例如安全专家）协商规划和设计。

* 根据保护需求和预期威胁级别，定义适当的安全架构、控制措施、对策和设计审查。这应由安全专家提供支持。

* 与其在应用程序和 API 中事后添加安全功能，不如从一开始就设计安全功能，这样更具成本效益。OWASP 推荐 [OWASP 速查表](https://cheatsheetseries.owasp.org/index.html) 和 [OWASP 主动控制](https://top10proactive.owasp.org/) 作为从一开始就将安全纳入设计的良好起点。

* 执行威胁建模，参见 [OWASP 速查表：威胁建模](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)。

* 教您的软件架构师安全设计概念和模式，并要求他们在设计中尽可能添加这些内容。

* 与开发人员一起检查数据流。

* 在所有其他用户故事旁边添加安全用户故事。

### 安全开发生命周期：

* 为了改进您的组织在构建应用程序和 API 时遵循的流程，OWASP 推荐 [OWASP 软件保证成熟度模型（SAMM）](https://owasp.org/www-project-samm/)。该模型帮助组织制定并实施针对其组织面临的特定风险量身定制的软件安全策略。

* 为您的软件开发人员提供安全编码培训，以及您认为有助于他们创建更健壮和更安全应用程序的任何其他培训。

* 代码审查，参见 [OWASP 速查表：安全代码审查](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html)。

* 为开发人员提供安全工具，然后教他们如何使用，尤其是静态分析、软件成分分析、密钥和 [基础设施即代码（IaC）](https://cheatsheetseries.owasp.org/cheatsheets/Infrastructure_as_Code_Security_Cheat_Sheet.html) 扫描器。

* 如果可能，为开发人员创建护栏（引导他们做出更安全选择的技术保障措施）。

* 构建强大且可用的安全控制措施是困难的。尽可能提供安全默认值，并尽可能创建"铺好的道路"（使最简单的方式也是做某事最安全的方式，成为明显的首选方式）。[OWASP 速查表](https://cheatsheetseries.owasp.org/index.html) 是开发人员的良好起点，许多现代框架现在都带有标准和有效的安全控制措施，用于授权、验证、CSRF 防护等。

* 为开发人员提供安全相关的 IDE 插件，并鼓励他们使用。

* 为他们提供密钥管理工具、许可证以及使用文档。

* 为他们提供一个私有 AI 使用，理想情况下设置一个包含有用安全文档的 RAG 服务器、您的团队为获得更好结果而编写的提示词，以及一个调用您组织首选安全工具的 MCP 服务器。教他们如何安全地使用 AI，因为无论您是否喜欢，他们都会这样做。

### 建立持续的应用程序安全测试：

* 测试技术功能和与 IT 架构的集成，并协调业务测试。

* 从技术和业务角度创建"正常使用"和"滥用"测试用例。

* 根据内部流程、保护需求和应用程序的假设威胁级别管理安全测试。

* 提供安全测试工具（模糊测试器、DAST 等）、安全的测试环境以及使用培训，或者为他们进行测试，或者聘请测试人员。

* 如果您需要高水平的保证，请考虑正式的渗透测试，以及压力测试和性能测试。

* 与开发人员合作，帮助他们决定需要从漏洞报告中修复什么，并确保他们的经理给他们时间来完成。

### 上线部署：

* 将应用程序投入运营，并在需要时从先前使用的应用程序迁移。

* 完成所有文档，包括变更管理数据库（CMDB）和安全架构。

### 运营与变更管理：

* 运营必须包括应用程序安全管理指南（例如补丁管理）。

* 提高用户的安全意识，并管理关于可用性与安全性之间的冲突。

* 规划和管理变更，例如迁移到应用程序或其他组件（如操作系统、中间件和库）的新版本。

* 确保所有应用程序都在您的清单中，所有重要细节都已记录。更新所有文档，包括 CMDB 中的文档以及安全架构、控制措施和对策，包括任何运行手册或项目文档。

* 对所有应用程序执行日志记录、监控和告警。如果缺少则添加。

* 创建有效和高效的更新和补丁流程。

* 创建定期扫描计划（希望是动态、静态、密钥、IaC 和软件成分分析）。

* 修复安全漏洞的服务水平协议（SLA）。

* 为员工（以及理想情况下您的客户）提供报告漏洞的途径。

* 建立一支训练有素的事件响应团队，了解软件攻击的样子、可观察性工具。

* 运行阻止或屏蔽工具以阻止自动化攻击。

* 每年（或更频繁）进行配置加固。

* 至少每年进行一次渗透测试（取决于您的应用程序所需的保证级别）。

* 建立用于加固和保护软件供应链的流程和工具。

* 建立并更新业务连续性和灾难恢复计划，包括您最重要的应用程序以及您用于维护它们的工具。

### 系统退役：

* 任何需要的数据都应归档。所有其他数据应安全擦除。

* 安全地退役应用程序，包括删除未使用的账户、角色和权限。

* 在 CMDB 中将应用程序的状态设置为已退役。

## 将 OWASP Top 10 作为标准使用

OWASP Top 10 主要是一份意识提升文档。然而，自 2003 年诞生以来，这并未阻止组织将其作为事实上的行业应用程序安全标准使用。如果您想将 OWASP Top 10 作为编码或测试标准，要知道它是最低限度的要求，只是一个起点。

将 OWASP Top 10 作为标准的困难之一在于，我们记录的是应用程序安全风险，而不一定是易于测试的问题。例如，[A06:2025-不安全设计](A06_2025-Insecure_Design.md) 超出了大多数测试形式的范围。另一个例子是测试是否实施了到位、在用且有效的日志记录和监控，这只能通过访谈和请求有效事件响应的样本来完成。静态代码分析工具可以查找日志的缺失，但可能无法确定业务逻辑或访问控制是否记录了关键安全漏洞。渗透测试人员可能只能确定他们在测试环境中触发了事件响应，而测试环境的监控方式很少与生产环境相同。

我们鼓励任何想要采用应用程序安全标准的人使用 [OWASP 应用程序安全验证标准](https://owasp.org/www-project-application-security-verification-standard/)（ASVS），因为它被设计为可验证和可测试的，并且可以在安全开发生命周期的所有部分使用。

ASVS 是工具供应商唯一可接受的选择。由于 OWASP Top 10 中几项风险的性质，工具无法全面检测、测试或防护 OWASP Top 10，参考 [A06:2025-不安全设计](A06_2025-Insecure_Design.md)。OWASP 不鼓励任何声称完全覆盖 OWASP Top 10 的说法，因为这根本不符合事实。
